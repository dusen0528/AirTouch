# 손 이동 + 표정 동작 조사

조사일: 2026-09-17 · 대상 소스: v0.4.0 · 상태: 조사 완료, 기능 미구현

## 결론

사용자가 원하는 조합은 **AirTouch로 손에 따라 커서를 이동하고, macOS의 ‘대체 포인터 동작’으로 표정 클릭을 수행하는 방식**이다. ‘헤드 포인터’는 머리로 커서를 이동하는 별도 기능이므로 이 조합에서는 끈다. Apple 문서는 대체 포인터 동작만 켜는 절차와 왼쪽·오른쪽·두 번 클릭, 드래그 앤 드롭을 설명한다. 기본 표정 동작 목록에 스크롤은 없다. [Apple 포인터 제어 설정](https://support.apple.com/ko-kr/guide/mac-help/unac899/26/mac/26), [표정으로 포인터 제어](https://support.apple.com/guide/mac-help/control-the-pointer-using-mouse-keys-mh27469/mac)

macOS의 표정 인식기를 앱에서 그대로 호출하는 공개 SDK는 이번 공식 문서·로컬 SDK 조사에서 찾지 못했다. 시스템 기능과 함께 쓰는 방법과 공개 영상 분석 API로 직접 표정을 판정하는 방법은 구분해야 한다. 현재 설치본이 두 기능과 함께 정상 동작한다는 뜻은 아니다.

| 방법 | 제공 범위 | AirTouch에서 필요한 일 | 판단 |
| --- | --- | --- | --- |
| macOS 대체 포인터 동작 | 시스템에서 표정을 판정해 클릭·드래그 실행 | 이동 전용 모드, 외부 입력과 드래그 조정, 카메라 동시 사용 확인 | 먼저 실험할 후보 |
| Vision 얼굴 랜드마크 | 눈·입 등 얼굴 좌표와 자세 | 표정 보정, 오인식 방지, 동작 상태 관리 및 입력 처리 | 앱 내부 통합 후보 |
| Core Image 얼굴 감지 | 웃음·좌우 눈 감김 결과 | 반복 클릭 방지, 자연스러운 눈 깜빡임과 의도 구분, 입력 처리 | 좁은 범위의 비교 후보 |
| ARKit 얼굴 블렌드셰이프 | iOS 계열의 얼굴 추적 | 네이티브 macOS SDK에서 사용 불가 | MacBook 내장 카메라 조건에서 제외 |

공개 API의 플랫폼·사용 가능 여부 및 컴파일 근거는 [얼굴 SDK 비교](face-sdk-options.md), 시스템 기능의 정확한 범위와 도입 시점은 [macOS 기능 조사](head-pointer-integration.md)에 정리한다.

## 현재 코드와 충돌할 수 있는 지점

아래는 소스에서 확인한 동작과 그로부터 예상한 통합 문제다. macOS 표정 입력을 실제로 관측한 결과는 아니다.

1. **표정 클릭 뒤 이동이 끊길 가능성.** [AppModel.swift](../../Sources/AirTouchApp/AppModel.swift)의 `physicalInput`은 AirTouch 자체 태그가 없는 마우스 이벤트를 받으면 제어를 1.5초 쉰다. macOS 표정 클릭이 이 모니터에 태그 없는 이벤트로 전달된다면 동일한 경로에 들어간다. 실제 마우스 조작에 제어권을 돌려주는 기능을 유지하면서 표정 입력과 구분할 수 있는지 확인해야 한다. 발신 PID만으로 구분할 수 있다고 가정하지 않는다.
2. **시스템 드래그와 손 이동의 연결.** [SystemTrackingController.swift](../../Sources/AirTouchApp/SystemTrackingController.swift)는 출력을 새로 시작할 때 왼쪽·오른쪽 버튼이 눌려 있으면 기다린다. [SystemInput.swift](../../Sources/AirTouchApp/SystemInput.swift)는 일반 이동에 `mouseMoved`, 자체 드래그에 `leftMouseDragged`를 보낸다. 시스템이 드래그를 시작한 상태에서 손 이동을 어떻게 이어받을지 별도 검증이 필요하다. AirTouch가 소유하지 않은 버튼을 임의로 해제해서는 안 된다.
3. **손 동작과 표정 동작의 중복.** 현재 손 제스처 엔진은 클릭·우클릭·드래그·스크롤까지 담당한다. 협업 모드에서는 이동과 선택한 스크롤만 남기고 버튼 동작은 한 주체가 맡도록 해야 한다.
4. **카메라 설정과 처리 부하.** [CameraService.swift](../../Sources/AirTouchApp/CameraService.swift)는 캡처 중 포맷을 유지하기 위해 기기의 configuration lock을 보유한다. Apple은 여러 앱의 카메라 공유 가능성과 장시간 잠금이 다른 앱에 영향을 줄 수 있음을 설명한다. 두 기능의 동시 실행 가능 여부, 실제 해상도·프레임 속도·지연을 측정해야 한다. [AVCaptureDevice 문서](https://developer.apple.com/documentation/avfoundation/avcapturedevice)

## 구현 전 확인 순서

첫 실험 범위는 **손 이동 + 표정 왼쪽 클릭 한 가지**로 제한한다. 표정 매핑은 미소 등 편하게 반복할 수 있는 동작을 사용자가 선택한다. 눈 깜빡임이 언제나 의도적인 입력이라고 가정하지 않는다.

1. 이동 전용 모드와 macOS 설정 안내를 분리한다. 설정에서는 대체 포인터 동작을 켜고 헤드 포인터는 끈 상태로 시작한다.
2. 같은 내장 카메라를 쓰는 상태에서 AirTouch 이동만 사용할 때와 비교한다. 두 기능의 시작 순서를 바꿔 캡처 중단, 포맷 변경, 지연을 확인한다.
3. 실제 표정 클릭이 이벤트 모니터에 어떻게 전달되는지 확인한다. 클릭 직후의 1.5초 멈춤과 중복 클릭을 먼저 해결한다. 손·얼굴 영상 및 원시 좌표는 기본 기록 항목으로 추가하지 않는다.
4. 클릭이 안정된 뒤 오른쪽·두 번 클릭, 드래그 시작 → 손 이동 → 표정으로 놓기를 실제 앱에서 확인한다. 물리 마우스 개입, 중지, 얼굴·손 놓침 때 버튼 상태도 확인한다.
5. 스크롤은 별도 선택으로 둔다. 초기에는 기존 손 스크롤을 유지하는 안이 단순하다. 모든 동작을 표정으로 옮기려면 스크롤 진입·방향·정지 방식을 추가로 설계해야 한다.

시스템과의 카메라 공유나 외부 드래그 조정이 안정적이지 않으면 앱 내부 인식으로 전환한다. 이때 기존 카메라 프레임을 Vision 또는 Core Image에 전달하고, 최신 프레임만 처리하는 독립 작업 경로에서 결과를 공통 입력 상태 관리로 합친다. 얼굴 분석 주기를 낮추는 것은 부하를 줄일 후보이며 실제 지연 개선이 검증된 설정은 아니다.

## 이번에 확인한 범위

- Apple 공식 기능 설명, macOS SDK 선언, macOS 14 대상 얼굴 API 컴파일 가능 여부를 확인했다. 재현 코드와 결과는 [얼굴 SDK 비교](face-sdk-options.md)에 기록한다.
- 기존 `SystemTrackingControllerTests` **8개 통과**. 가짜 입력 출력기로 버튼이 눌린 상태의 획득 대기와 일시 정지 후 재개 등 기존 제어 동작을 확인했다. 실제 표정 인식, 카메라 공유, Finder 등의 입력 반응을 증명하지 않는다.
- 이 조사로 앱 소스, 설치본, macOS 설정은 변경하지 않는다. 배포 버전과 릴리스 태그도 유지한다.

후속 구현은 이동 전용 모드, 표정 협업, 드래그 연결, SDK 내부 인식 실험을 각각 검증 가능한 변경으로 나눠 한글 커밋으로 기록한다.

기존 입력 제어 테스트 재현:

```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer swift test --filter SystemTrackingControllerTests
```
